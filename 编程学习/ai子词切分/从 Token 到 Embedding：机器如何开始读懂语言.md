# 从 Token 到 Embedding：机器如何开始读懂语言

学习之前，先想明白：为什么需要 **token**？

## 人类语言，机器看不懂

首先有一个最根本的问题：

计算机和人之间，有一道天然的鸿沟。

- 你说：今天天气好
- 计算机：`0 1 0 1 0 1 1 1 ...`

计算机根本无法直接理解我们所说的文字、语义、情感等等。它最终只能处理数字。

所以，我们首先要解决的问题就是：

> 怎么把人类语言，切成机器能处理、能进一步理解的块？

这个“块”，就是 **token**。

## 语言可以怎么切？

### 第一种：按字符切（Character-level）

```js
// 输入
"I love you"
// 切法
['I', ' ', 'l', 'o', 'v', 'e', ' ', 'y', 'o', 'u']
```

每个字符 = 1 个 **token**。

- 优点：简单粗暴，词汇表极小，只需要几十个字母加符号。
- 缺点：一个字母本身几乎没有意义。机器每次都要重新把各个字母拼起来，理解组合后的含义，负担很重。

### 第二种：按单词切（Word-level）

```js
// 输入
"I love you"
// 切法
['I', 'love', 'you']
```

每个单词 = 1 个 **token**。

- 优点：单词本身的意义很清晰。
- 缺点：
  1. **词汇表爆炸**：英语有几十万个单词，再加上人名、地名、网络新词等等，词汇表会不断膨胀。
  2. **遇到没见过的词就麻烦**：如果训练时没见过 `hzh` 这个词，传统的按词切分通常只能把它变成一个 `[UNK]` 标记，信息基本就丢了。
  3. **丢失单词内部的结构**：比如 `unhappiness` 是由 `un + happy + ness` 这些部分组成的。按整个单词切，内部可以复用的结构就被忽略了。

字符切得太碎，单词又切得太大。于是就有了一个很实用的折中方案。

### 第三种：子词切分（Subword）

核心思想是：**高频的词，尽量保持完整；低频的词，拆成更小的片段。**

```text
高频词 "the"              -> 保持完整 -> ['the']
低频词 "unhappiness"      -> 拆开     -> ['un', 'happi', 'ness']
罕见词 "transformerify"   -> 细拆     -> ['transform', 'er', 'ify']
```

这里要注意：子词片段**不一定天然有含义**。像 `un-`、`-ness`、`-ify` 这样的片段，确实常常和词义或词形有关；但 BPE 这类算法本质上是按统计频率切分，切出来的 `happi` 之类片段未必是一个完整、有意义的部件。

不过，它仍然很有用：模型可以复用常见的字母组合和词形模式，因此面对从未见过的新词时，不至于完全束手无策。

![[编程学习/ai子词切分/1.png]]

给上面打个比喻：你给女朋友介绍一下这道可乐鸡翅怎么做。

- **按字符切**：你把鸡翅切成肉末，不了解的人都不知道它之前是鸡翅。
- **按单词切**：你把整只鸡丢锅里了，太完整，没法灵活处理。
- **子词切分**：你把鸡翅按部位处理后再去炒，既保留了一些结构，也能灵活组合。

所以，子词切分不是放之四海皆准的“最优解”，但它在词汇表大小、表达能力和处理生词的能力之间，提供了一个很常见、很实用的平衡。

那机器到底怎么知道该在哪里切？哪些片段值得保留？这就是 **BPE（Byte Pair Encoding）** 要解决的问题。

## BPE：从数据压缩到子词词表

**BPE** 不是为了语言发明的，它早期和语言没有半毛钱关系。

1994 年，一个叫 **Philip Gage** 的人提出了 BPE。当时它的目的，是做**数据压缩**。

原理很简单：在一堆数据里，找到出现最频繁的一对相邻符号，把它们合并成一个新符号。反复执行，数据就能被压缩。

到了 2016 年，**Sennrich** 等人发现：这个过程和自动构建子词词汇表的思路很像。于是 BPE 被引入 NLP 领域，后来也成为许多大语言模型常用的分词方案。

BPE 的核心思想是：**从最小单位开始，反复合并出现频率最高的相邻对，直到词汇表达到预定大小。**

下面画个流程，看一下 BPE 是怎么做的。

### 第一步：初始化

先把每个词拆成最小单位。

![[编程学习/ai子词切分/2.png]]

### 第二步：统计频率

统计所有相邻对出现的频率。

![[编程学习/ai子词切分/3.png]]

### 第三步：合并最高频的相邻对

例如，把 `e s` 合并成 `es`。

![[编程学习/ai子词切分/4.png]]

然后不断重复上述步骤。

比如，相邻的 `es t` 出现次数也是 9 次，那就组成 `est`。此时的词汇表是：

```text
词汇表 = { l, o, w, e, r, n, s, t, i, d, _, es, est }  共 13 个
```

继续重复，`est _` 出现 9 次，合并：

```text
词汇表 = { l, o, w, e, r, n, s, t, i, d, _, es, est, est_ }  共 14 个
```

再继续，`l o` 出现 7 次、频率最高，合并成 `lo`；再重复，`lo w` 又出现 7 次，合并成 `low`。

发现没？`low` 就这样被拼出来了。

BPE 通过频率统计，找到了语言中反复出现的“拼装模式”。但它学到的首先是**统计上的常见组合**，不是词典里预先定义好的语义；这些 token 后续能表达什么含义，要等模型训练时再慢慢学出来。

## Token 变成编号后，还缺什么？

BPE 切完之后，我们得到了一堆 token 碎片。为了方便说明，假设：

```text
"I love you" -> ['I', 'love', 'you']
```

注意，这只是一个示例。真实模型如何切分，取决于它自己的词表和分词器。

接着，我们给每个 token 一个数字编号：

```text
token  编号
I      0
love   1
you    2
hate   3

现在 "I love you" -> [0, 1, 2]
```

机器现在能处理整数了，但问题还没有解决。

编号只是一个**身份标识**，它本身并不携带词的信息。比如 `love` 和 `hate` 的编号差是 2，`you` 和 `love` 的编号差是 1；难道就能说明 `you` 和 `love` 更接近吗？显然不能。

我们知道，`love` 和 `hate` 虽然意思相反，但在语义讨论中往往是相关的；而编号的远近，和这种关系没有任何关系。

所以，我们需要一种表达方法，能让**语义或用法相近的内容，在数学上也更接近**。

这就是 **Embedding（嵌入）** 要做的事。

## Embedding：给 token 一组可学习的数字

Embedding 的核心思想是：

> 用一组多维数字来描述一个 token，让模型可以在数学空间中表示和计算语言信息。

举个简单例子：

![[编程学习/ai子词切分/5.png]]

这只是一个简化示例。在现在的大语言模型中，每个 token 不止用 4 个**维度**描述，通常会用几千到上万个维度。

那这些数字是怎么定义的？

并非人手动定义，而是训练出来的。

![[编程学习/ai子词切分/6.png]]

一开始，每个 token 的向量通常是随机初始化的。然后模型开始阅读海量文本，反复看到：

```text
"I love my cat"
"I love my dog"
"I love this song"
"I hate this weather"
"I hate waiting"
"she loves dancing"
```

在训练过程中，模型会为了更好地预测文本中的下一个 token，不断调整这些向量和其他参数。于是，出现在相似上下文中的词，往往会形成某种相近或相关的表示。

不过，这里还要再区分一下：

- 输入时，每个 token 确实有一个固定的初始 Embedding。
- 经过 Transformer 多层计算后，模型得到的是**结合上下文的表示**。

也就是说，同一个词在不同句子里的含义，模型最终看到的表示可以不同。比如 `apple` 在“吃一个 apple”和“Apple 发布新品”里，就不应该被当成完全一样的意思。

## 向量还能做“词义加减法”吗？

当 Embedding 学得足够好时，有时会出现一个很有趣的现象：**向量之间可以表现出某些词义关系。**

2013 年，Mikolov 等人在 Word2Vec 的研究中展示过一个经典例子：

```text
king - man + woman ≈ queen
```

看起来不可思议，但它表达的是：把 `king` 的向量减去 `man` 的向量，再加上 `woman` 的向量后，得到的新向量用相似度去查找时，可能最接近词汇表中的 `queen`。

这并不意味着模型里真的有一根清晰、固定的“性别坐标轴”。更准确地说，是模型从大量文本的统计关系中，学到了一些和性别、身份、关系等有关的方向或模式。

从这里也能看到整条链路：

> **tokenization** 把文本切成 token；**BPE** 帮我们构建常用的子词词表；**Embedding** 再把这些 token 变成模型能学习和计算的向量。

机器并不是一开始就“懂”语言，而是先把语言拆成可处理的单位，再在海量数据里一点点学会这些单位之间可能存在的关系。


## 总结：

这篇文章从“机器为什么不能直接理解人类语言”切入，解释了 token 的作用。随后对比按字符、按单词和按子词切分的优缺点，引出BPE 如何通过统计高频相邻字符对来构建子词词表。最后说明 token 先被映射为编号，再通过 Embedding 变成可学习的向量；现代大语言模型还会结合上下文，形成更动态的语义表示。
