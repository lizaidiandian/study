当我们运行这段代码时,究竟发生了什么?

一般认为就是: 代码 -> 运行,这当然不对了,中间还有许多步骤

**CPU 只认识一种语言**

我们所写的: a = b + c

CPU看到的(x86 机器码):
	8B 45 F8
    03 45 F4
    89 45 EC

这是十六进制表示的二进制,不同的CPU(x86、ARM) 有各自的机器码格式,所有彼此之间完全不兼容

那么 CPU 只认识机器码,那在 翻译 的时候,是 每次运行时翻译 ,还是 运行之前就翻译 好?各自的优势是什么?
1. 每次运行时翻译
	- 运行速度:慢,因为他是边跑边翻译
	- 磁盘占用:小,存源代码
	- 可移植性:强,在哪都能跑
2. 运行之前就翻译
	- 运行速度:快,因为他是直接翻译
	- 磁盘占用:大,存机器码
	- 可移植性:弱,绑定平台

在上一篇文章中有提到两者结合的方法: java
- Java -> 先编译成字节码 -> 运行 JVM 翻译(兼顾可移植性)
- JIT 尽量减少运行时翻译的损耗

.exe 不只有机器码

它的文件结构分为:
1. 文件头(header):描述这个程序的基本信息,加载到内存的哪个位置等
2. 代码段(.text):真正的机器码,CPU 执行的部分
3. 数据段(.data):全局变量、字符串、常量等
4. 重定位信息

那么,CPU是怎么知道你读取的是 代码段 还是 数据段?

诶, CPU 内部有一个专门的寄存器，叫**程序计数器(PC)**

程序计算器的作用:永远指向"下一条要执行的指令的地址"

它如何指使 CPU 工作
1. 去 PC 指定的地址取数据
2. 执行
3. PC 自动 指向下一条
4. 重复第一步

由 **程序结构** 来保证 PC 要指向代码段里跑,由 OS 把 PC 对准 .text 的入口

```c
int add(int a,int b){
```

```c
}
```
生成的 main.obj 文件会出现一个问题
- 调用 add 函数
- 发现 main.obj 里面没有这个函数,也不知道 add 最终在内存哪个地址上
- 返回 空

上两个 .obj 文件都是一个半成品,看到这里能发现,那我让 main.c 找到 add函数不就好了

链接器出现了,负责把半成品拼成完整程序

```text
main.obj + math.obj  -> [链接器] -> main.exe
```

这里补一个知识点: `CALL [你的变量或函数地址]` 对应了 add(int a,int b),还记得,定义变量或函数的时候,其实就是在内存中开辟了一段空间给你,并带有地址

他负责做的事有:
1. 把所有的 .obj 的机器码拼在一起
2. 扫描所有的"空地址"
3. 输出完整的 .exe

那么,如果调用一个函数,但忘记把那个函数所在的 .obj 交给链接器,会在 编译阶段报错 还是 链接阶段报错?

答案是: 链接阶段报错

编译阶段检查:
- 语法是否正确,类型对不对
- 函数有没有声明

链接阶段检查:
- 所有被调用的函数,实现能找到吗?

那新的问题来了

```c
int main(){
```

这并没有定义 add函数啊,为什么不报错?

这是因为之前的 **C 语言的"隐式声明"规则**

他做了什么?他会自动假设
```text

继续编译，留下 CALL [????]
```

但到现在已经不行了,这个规则被废除了,那现在是如何解决的?

头文件<.h>,把声明单独放到头文件里,#include进来,先让编译器提前知道函数的存在

DLL 文件与导入库

之前的有个问题 .lib 是静态链接,代码是直接复制进 .exe的

但 Windows API 用的另一种机制

```
程序A.exe 内含 add 代码 +3MB
程序B.exe 内含 add 代码 +3MB
程序C.exe 内含 add 代码 +3MB
```
同时运行时,内存存了三份一模一样的代码,浪费内存空间

DLL的解法:代码只保存一份,所有程序共享
```
user32.dll 内含 add  -> 程序A
					-> 程序B
					-> 程序C
```
链接时,你提供的 .lib 不包含函数代码,只包含一条信息
```text
add 这个函数在 user32.dll 里,运行时去那里找
```

编译链接后的 .exe:
- CALL [???] ->地址先空着,运行时去 user32.dll 去找 add

那好处和坏处分别是什么?

好处:
1. 所有依赖它的程序,下次运行时自动用心版本
2. 不需要每个程序单独更新

坏处:DLL Hell(DLL 地狱)

他是怎么回事?
```text
程序A 安装时,附带 foo.dll 版本 1.0

程序B 安装时，覆盖掉了 foo.dll，换成 2.0

结果:程序A 运行时加载 foo.dll 2.0版本
	把1.0中某些函数的行为给改了,然后逻辑不通 -> 崩溃
```
那如何解决的

微软引入了 并行程序集:
```text
不同版本的 DLL 可以同时存在于系统中
每个程序明确声明自己要用哪个版本
互不干扰
```


.exe 文件 已经有机器码了,还不能直接执行,因为 **编译时不知道自己会被加载到哪里**

假设:
```
程序里有一个变量 a,地址是多少?

编译器:不知道
```
运行时内存里可能已经有其他程序了,你的程序会被加载到哪个地址,这无法预知

解决办法,记录 **偏移量**,运行时再算真实地址

.exe 里不写绝对地址,写相对偏移

比如:"变量 a 在程序起点往后 100 字节处"

加载器会怎么做?
- 假设程序被加载到 0x00400000
- 变量 a 的真实地址 = 0x00400000 + 100 = 0x00400064

就算下次程序被加载到了  0x00600000
- 变量 a 的真实地址 = 0x00600000 + 100 = 0x00600064

那问题来了,如果程序A 和 程序B都想要加载到同一个地址,怎么处理?

答案:"强行错位"

回想上一章的 虚拟内存 ,这里要补上章 虚拟内容 没讲的内容:地址空间隔离
给每个程序一个"独立的假地址空间"

```
程序A 以为自己在：  0x00400000 -> MMU -> 实际读取物理地址:0x10000000
程序B 以为自己在：  0x00400000 -> MMU -> 实际读取物理地址:0x20000000
```

所以问题解决了:
- 重定位信息  → 解决"不知道加载到哪"
- 虚拟内存    → 解决"两个程序地址冲突"
