
首先,先知道一个概念: 运行环境 = 操作系统 + 硬件

那么,先提出一个问题:你写了一个程序,为什么它不能在任何地方运行

程序运行需要 操作系统 和 硬件 同时满足条件

想象一个场景: 
- 程序 是一道菜 
- CPU 是厨师
- 操作系统是厨房

目标: 把这道菜放进去烤箱烤10分钟

场景一: 厨房有烤箱 -> 顺利执行

场景二:厨房没有烤箱,只有高压锅 -> 出现问题 -> 无法执行
1. 高压锅不知道"烤箱"是什么指令(也就是CPU不兼容)
2.  "烤"这个操作根本没有（OS API不存在）

那么这个问题会出现什么后果?

写一个软件,要针对每种平台都写一遍,开发成本极高

那么如何解决这个问题

1.window:消灭 CPU 之外的硬件差异

核心概念:不让程序直接去操作硬件,否则必须为每一种硬件组合写不同的代码

解法逻辑:
```text
程序(只调用 windows api) -> windows 系统调用层 -> 驱动程序层 -> 实际硬件

windows 系统调用层:所有程序看到的接口都一样
驱动程序层(NAVDIA驱动 AMD驱动):由硬件厂商负责写,对上统一接口
实际硬件:如显卡 声卡 网卡
```

windows 就像翻译官,程序说要 "播放声音",windows就把这句话翻译成不同的方言,告诉下面的驱动程序层

2.Linux:源代码分发

我们先来看一个问题,windows 确实解决了 "同一 OS 下的阴间差异",但 OS 本身之间的差异仍然存在

比如:Windows 和 Linux 

目标:打开一个文件
```text
Windows：
    HANDLE h = CreateFile("data.txt", GENERIC_READ, ...);
    
Linux：
    int fd = open("data.txt", O_RDONLY);
```

可以看出,CPU相同,但无法在不同的 OS 下执行另外的 OS 的相同功能代码的程序

那么 运行环境变得更清晰了

运行环境 = CPU 架构 + 操作系统

那Linux的源代码分发是怎么做的?

不分发编译好的程序，直接分发源代码，让用户在自己的机器上编译
- 传统方式  [x86 + linux] -> x.exe -> [arm + linux] 无法运行 
- linux方式 .c -> [ARM/x86  + linux / windows] 本地编译器 -> 生成本机可执行文件 

- 优点:自动适配本机 CPU 和 OS,兼容性高
- 缺点:用户需要使用编译器,使用程序门槛变高

这种方式不太好,使用门槛变高,会变相的流逝很多客户,那么Java 虚拟机出现

Java 虚拟机:一次编写,处处运行

他的做法是这样的: 创造一个 "中间层",再有中间层适配各种环境

这和上面的windows做法很像,也是 程序 调用 windows api 去访问 windows 系统调用层,也挺符合 设计模式 的开闭原则:对**新增**开放 ,对**修改**关闭

```text
传统编译: 源代码 -> 编译器 -> x86机器码、ARM

java:    源代码 -> java编译器 -> 字节码 -> x86 JVM 、 ARM JVM
```

1. 字节码:不是任何真实 CPU 的机器语言,它是专门为 JVM 设计的"虚拟 CPU 的指令集"
2. JVM(Java Virtual Machine，Java VM):也叫Java虚拟机,Java虚拟机会将Java字节码逐一转换为本机代码来执行

这么说有点抽象,
- 字节码: 就像"普通话"
- CPU: 对应的 "各个方言"
- JVM:则对应能够**听懂普通话**的人,然后再把普通话翻译成 CPU 能够听懂的**方言** 在执行

那代价就是,性能消耗

原本执行机器码的流程:CPU → 指令 → 执行

JVM执行字节码:CPU → JVM解释字节码 → 翻译成机器码 → 执行

云计算:按需租用运行环境

核心概念：不搬程序，搬环境——把运行环境变成一种可以出租的服务

可分为:SaaS、PaaS、IaaS
- SaaS（Software as a Service，软件即服务）​
	你直接用软件，什么都不用管
- PaaS（Platform as a Service，平台即服务）
	提供操作系统和运行时，你只管部署代码
- IaaS（Infrastructure as a Service，基础设施即服务）
	提供虚拟机（CPU + 内存 + 硬盘），你自己装操作系统和软件

Saas就像是去饭店吃饭。Paas是在厨房，工具给你配好了。Iaas 是厨房都没有，什么都要自己来做


最后，还有个最根本的问题：电脑刚通电，操作系统还没有加载到内存中来，谁来启动系统？

这有点像“先有鸡还是先有蛋”的问题

没有运行操作系统我怎么写进内存，操作系统没在内存我怎么运行

这时，BIOS 出现了，它自己内部有写入固定的程序。

它是这样做的
1. 自检硬件：检查CPU、内存、硬盘是否正常
2. 找到启动设备(一般是硬盘,也有u盘)
3. 读取第一个扇区的内容(扇区的话就是硬盘的存储空间的样子)

引导并装入程序(Bootloader):比如windows Boot
1. 被 BIOS 加载到内存中
2. 找到操作系统的内核文件
3. 把操作系统加载进内存 (先有鸡还是先有蛋的问题解决了)

这个过程被叫做 自举（Bootstrap）:用一个小程序拉起一个更大的程序,一次又一次,最终把操作系统拉起来

打个比方:就像学习,你不会一上来就什么都会,而是有许许多多的基础知识,来理解更高级的知识
