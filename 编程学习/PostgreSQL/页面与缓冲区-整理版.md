# 页面与缓冲区：PostgreSQL 怎么在快和不丢数据之间取平衡？

前两篇讲的是 PostgreSQL 能帮我们做什么，这篇想搞懂的是：它为什么能做到**查询不必每次都碰磁盘**，又能在断电或崩溃后尽量把数据恢复回来？

前面讲 Redis 时提过 AOF 和 RDB：一个偏向记录操作，一个偏向定期做快照。PostgreSQL 的持久化思路和它们有一点相似，但实现上更围绕数据库的页面和日志来展开。

## 数据库为什么按“页”读数据

数据库的全部数据最终都在磁盘上。要是每查一条数据都去读一次磁盘，速度肯定跟不上，所以 PostgreSQL 会在内存里维护一块叫 **Shared Buffers** 的缓冲区。

它的作用很直接：把磁盘中的数据先搬一份到内存里，之后读和改都优先操作这份内存副本。

不过，磁盘和内存之间搬数据，并不是一行一行地搬。PostgreSQL 的基本搬运单位是**页**，也常被叫作数据块；默认一页是 **8KB**。

- **页**：从磁盘加载到内存、以及从内存写回磁盘时的基本单位。
- **脏页（dirty page）**：内存里已经被修改过、但还没有写回磁盘的页面。例如执行一次 **UPDATE** 后，对应页面就可能变成脏页。

![[20.png]]

所以一次读写大致是这样：

**读数据时**，PostgreSQL 会先去 Shared Buffers 找目标页面。找到了，就是缓存命中，直接从内存读；找不到，才从磁盘把整个 8KB 页面加载到缓冲区。

**改数据时**，它改的是内存中的页面副本，而不是马上改磁盘文件。这个页面会被标记为脏页，意味着内存内容已经比磁盘上的版本新了。

**缓冲区满了时**，系统需要腾位置。干净页可以直接淘汰；脏页不能直接丢，得先写回磁盘，之后才能腾出位置。

这样做解决了速度问题，但也带来了一个很现实的问题：脏页还没写回磁盘时，要是突然断电，刚才的修改不就没了吗？

## 脏页没落盘，数据靠什么保住

这里就轮到 **WAL** 登场了。WAL 全称是 Write-Ahead Logging，意思是**预写日志**。

它的核心规则是：在修改真正的数据页之前，先把“准备做什么修改”记到 WAL 日志里，并让这段日志先具备可恢复性。

![[21.png]]

那为什么不干脆直接把数据页写回磁盘？核心原因是**写入方式不同**。

数据页散落在数据文件的不同位置，修改它们往往意味着随机写；而 WAL 是按时间顺序不断追加的日志，写入更连续。对磁盘来说，连续地追加日志通常比到处修改数据页更高效。

所以 PostgreSQL 把“先保证日志安全”和“之后再慢慢刷脏页”拆开了：前者负责保证修改不会凭空消失，后者负责最终让数据文件跟上内存里的最新状态。

## 一次提交时，真正先落盘的是什么

那么执行 **COMMIT** 时，到底发生了什么？

![[22.png]]

在默认配置下，**COMMIT** 返回成功时，PostgreSQL 主要保证的是：这次事务对应的 **WAL 已经持久化**。它并不要求所有脏页也在这一刻写回数据文件。

这就是 WAL 的意义：即使脏页还在内存里、还没来得及回写，机器突然断电，数据库重启后也可以从最近一次检查点之后开始读取 WAL，把已经提交过的修改重新应用到数据页上。

换句话说，数据文件可以暂时没更新到最新，但只要相应日志还在，数据库就知道该怎么把它补回来。没有提交成功的修改，则不会被当作已完成事务保留下来。

## 最后收一下

如果只用一句话理解页面、缓冲区和 WAL 的关系，那就是：**页面和 Shared Buffers 让 PostgreSQL 读写得更快，WAL 则让它不必每改一次数据都立刻写盘，也能在出问题后找回已经提交的修改。**

数据库不是完全不写数据文件，而是把“先记住这次改了什么”和“把最终数据写回去”分成两步。前一步保证可恢复，后一步完成真正的落盘；两者配合起来，才让 PostgreSQL 能同时兼顾性能和可靠性。
